# Final Reflection: Missions 1 to 10

At the start of this course, I honestly thought the cloud just meant renting someone else's computer. Ten missions later, I see how much more there is to it. Mission 1 covered the basics: what cloud computing is, how it's different from owning hardware, and the service models (IaaS, PaaS, and SaaS) that kept coming up later. In Mission 2, I made a cloud infrastructure blueprint, and it taught me to plan first by figuring out what a system needs, like compute, storage, and networking, and how those parts connect. Mission 3 had me comparing providers like AWS and Azure side by side. I learned that no provider is the best at everything. The right pick depends on cost, features, and what the client needs. Those first three missions gave me the vocabulary and the big picture.

Mission 4 is where things got hands-on. I ran my first Docker container and watched Nginx respond within seconds, which made it clear why people choose containers over setting up a whole VM. In Mission 5, I deployed MinIO for object storage and hit a real problem: the image the lab told me to use wasn't on Docker Hub anymore, so I had to track it down on quay.io. Mission 6 introduced Docker Compose and Infrastructure as Code. Mission 7 taught me to read logs and metrics to check whether an app is healthy. In Mission 8, I locked down a server with UFW and a Default Deny policy, and in Mission 9, I wrote a Bash script and used cron so backups run without me.

Mission 10 put everything together, and this time there were no step-by-step instructions. I built an Ubuntu Server VM in VirtualBox, ran WordPress and MariaDB on it with Docker Compose, secured it with UFW, and scheduled nightly database backups. The hard part wasn't any one command. It was figuring out how the pieces fit, because networking, volumes, firewall rules, and automation all depend on each other. Writing the operational manual also showed me that a system isn't really finished until someone else can run and maintain it.

My favorite role was Cloud-Native Engineer, because it was the first time the cloud felt real to me. I pulled an Nginx image, started it with one command, and had a working web server in seconds, something that would have taken a full VM and a lot of setup. I could also see exactly what was going on, since I could list the container, stop it, and remove it, and I knew what each command did. Containers ended up being the foundation for almost every mission after that, from MinIO and Docker Compose to the WordPress stack in my final project, so this was the mission that made the rest click. The biggest change in how I think is that cloud engineering isn't about memorizing commands. It's about understanding why each layer exists and knowing how to troubleshoot it when something breaks.

My GitHub portfolio shows that progress. It started as simple notes and grew into a set of documented projects with commands, screenshots, and reflections. I can look back at it as proof of what I can build, and I plan to keep adding to it.
